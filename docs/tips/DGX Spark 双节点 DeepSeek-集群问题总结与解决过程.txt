============================================================
二、发现的问题 1：MASTER_ADDR 配置错误
============================================================

现象：

检查 runtime/.env.dspark：

发现：

    MASTER_ADDR=192.168.101.10


但是 cluster.env 中定义：

    HEAD_R1=192.168.100.10

并且项目规则：

    MASTER_ADDR 必须等于 HEAD_R1


原因：

render-env.sh 之前生成的 .env.dspark 没有同步最新 cluster.env。

导致：

head / worker 的 rendezvous 地址可能走错误的 Rail 2 网络。


解决：

重新生成环境文件：

Master:

    cd ~/dgx-spark-2x-deepseek-v4-flash

    bash runtime/render-env.sh head


Worker:

    ssh ieta-spark02.local

    cd ~/dgx-cluster/runtime

    bash render-env.sh worker


确认：

    MASTER_ADDR=192.168.100.10

    VLLM_HOST_IP:
        Master = 192.168.100.10
        Worker = 192.168.100.11


验证：

    bash runtime/preflight.sh worker


结果：

    preflight passed (worker)


说明：

NCCL/Gloo/MASTER_ADDR 配置正确。

四、问题 3：外部 LAN 无法访问 vLLM API
============================================================

现象：

本机：

    curl http://127.0.0.1:8000/health


成功：

    HTTP/1.1 200 OK


检查监听：

    ss -ltnp | grep 8000


结果：

    LISTEN 0.0.0.0:8000


说明：

vLLM 已经绑定所有 IPv4 地址。


检查 Docker：

docker-compose:

    network_mode: host


说明：

没有 Docker NAT 问题。


检查 vLLM 启动参数：

    --host 0.0.0.0
    --port 8000


正确。


============================================================
五、真正原因：HTTP Proxy 环境变量导致误判
============================================================

测试：

执行：

    curl http://200.0.0.101:8000/health


失败。


原因：

curl 输出：

    Uses proxy env variable http_proxy

    http_proxy=http://202.0.0.114:4780/


请求实际上：

错误路径：

    Client
       |
       |
       v
    HTTP Proxy
    202.0.0.114:4780
       |
       X
    200.0.0.101:8000


不是：

    Client
       |
       |
       v
    200.0.0.101:8000


解决：

绕过代理：

    curl --noproxy '*' \
         http://200.0.0.101:8000/health


结果：

    HTTP/1.1 200 OK


证明：

vLLM 服务完全正常。

============================================================
七、最终结论
============================================================

问题不是：

    ❌ vLLM host 配置

    ❌ Docker 网络

    ❌ docker-compose

    ❌ network_mode

    ❌ UFW firewall

    ❌ NCCL

    ❌ Gloo

    ❌ cluster.env


真正问题：

    HTTP Proxy 环境变量影响 curl / 浏览器访问。


解决方式：

1. 保持集群配置不变：

    MASTER_ADDR=192.168.100.10

    NCCL_SOCKET_IFNAME=enp1s0f1np1

    GLOO_SOCKET_IFNAME=enp1s0f1np1


2. 在访问 API 的机器配置 NO_PROXY：

Linux:

    export NO_PROXY="
    localhost,
    127.0.0.1,
    ::1,
    200.0.0.0/24,
    192.168.100.0/24,
    192.168.101.0/24
    "

    export no_proxy="$NO_PROXY"


或者写入：

    ~/.bashrc


3. 浏览器访问：

    将：

        200.0.0.101

    加入浏览器代理 bypass 列表。
